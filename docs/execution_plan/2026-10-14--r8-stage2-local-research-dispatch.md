## 2. 共同規則（U1、U2、U3 適用）

### 2.1 身分與基線

1. 每個單元是一個獨立的交付，`work_item_id` 與 `lane_id` 用該單元標題所列的名稱，不要改名，也不要為同一單元另立第二個名稱。
2. 先 `git fetch origin`。三個單元都從**同一個** main commit 開工，就是含有本文件的那個 main；把完整 commit 記下來，各單元的 task contract 與 context 都綁它。
   main 上找不到本文件就停止並回報 `NEEDS_CONTEXT`。
3. task contract 的 surfaces 必須含 `agent_workflow`，並帶成對的 `work_item_id` 與 `lane_id`；否則准入不會建立交付記錄，受控審查工具會拒絕受理。
4. 各單元改動的檔案互不重疊（見各單元的「可改檔案」）。每個單元一個自己的 worktree、一個自己的分支。
5. 一個單元停止或失敗時，保留它的 patch 與停止原因，繼續其他單元。停止的單元不得另立名稱重來。

### 2.2 程式與測試的環境

- U1、U2 的程式只用 Python 標準函式庫；測試另外只用 pytest。實作者那邊的受控測試驗證在這台開發機上缺少第三方套件，
  只用標準函式庫，受控驗證才有機會執行。U1、U2 各有一個測試以 AST 檢查自己的模組只匯入標準函式庫與本套件，
  因為 CI 的環境裝了 numpy 與 pandas，不能靠環境把關。
- 最低支援 Python 3.10（這台開發機是 3.10，CI 是 3.12）：不要用 `datetime.UTC`、`tomllib` 等 3.11 才有的功能。
- 本機在倉庫根目錄執行：`python3 -m pytest -q program_code/research/tests/test_r8_<單元>.py`。
  根目錄 `pytest.ini` 的 `asyncio_mode` 在沒有 pytest-asyncio 的環境會出現未知設定的警告，屬預期，不是失敗。
- 受控測試驗證仍無法執行時，實作者在代碼審查通過後停止，把提交留在本機分支並回報；獨立測試驗證、發布與自動審查留言由記錄者處理。

### 2.3 不要碰的檔案

- `TODO.md`、`docs/` 下的任何檔案、`helper_scripts/SCRIPT_INDEX.md`、`CHANGELOG.md`。文件收尾由記錄者處理。
- 既有的測試檔，例外只有 U3「可改檔案」明列的兩個，且只能做 U3 寫明的修改。
- 各單元「可改檔案」以外的任何檔案。需要改到清單外的檔案才能完成時，該單元停止並回報。
- 治理源碼、任何准入帳本、租約或審查狀態檔；回放（`rust/openclaw_engine/src/replay/`、`control_api_v1/replay/`）與 production 熱路徑。

### 2.4 計時器

1. **租約**：取得時指定 `--ttl-seconds 86400`（上限）。每次提交之前與發布之前各查一次 `status`；剩餘時間不足一半就先續租。
2. **審查時段**：從該交付第一次審查呼叫起算，standard 為 3600 秒。第一次審查之前，把實作與自己的驗證全部做完並提交，之後連續送審。
3. 每個審查節點至多兩次呼叫，複核的提問須與初審逐字相同，所以提問用檔案路徑指向受審內容，並寫明「讀當次提交中的版本」。
4. 修補會讓上游審查的通過失效：下游提出阻塞而修補之後，先複核上游，再複核下游。估計放不進剩餘時段時，在送出複核**之前**停止並回報。

### 2.5 不變量

- 測試不發任何網路請求：以注入的假傳輸層模擬回應，並在測試中封鎖 socket 連線，有連線即失敗。
- 實作者不執行實際取數；取數由記錄者在 U1 合入 main 之後依 §4 執行（P3）。
- 不連 Linux、資料庫、Demo 或 live；不部署。
- 新增的註釋用中文；不硬編機器路徑；輸出位置一律由命令列參數指定；不提交任何資料檔或金鑰。
- 倉庫是公開的：不得在程式、測試或 PR 說明中寫入本機絕對路徑。

### 2.6 交付

- 自己的流程走完（代碼審查與測試驗證都通過）時：推送自己的分支，開 **draft** PR，標題以 `R8 S2 U<n>` 開頭。不直接推 main，不自行合併。
- 受控測試驗證無法執行時：見 §2.2 末項。
- 回報與 PR 說明寫明：改了什麼、測試的四個數字（passed／failed／skipped／error）、測試是受控擷取還是直接執行、審查結論、未驗證的範圍、
  開始與結束時間（UTC）與投入工時。跑不了或跳過的檢查要明說，不要寫成通過。

## 3. 實作者的三個單元

### U1 `R8-S2-PUBLIC-DATA-20261014`：公開行情取數工具

**為什麼**：修訂二 N3 要求研究資料直接取自交易所公開來源，存為記雜湊的本機檔案，不經資料庫，並記錄請求來源。
既有的回放公開資料客戶端不取資金費與持倉量歷史，Rust 的回填工具寫入資料庫，兩者都不合用。

**可改檔案**（全部新增）：`program_code/research/r8_data/__init__.py`、`program_code/research/r8_data/public_data.py`、
`program_code/research/r8_data/stage2_plan.json`、`program_code/research/tests/test_r8_public_data.py`。

**要求**：

1. 基底網址只允許 `https://api.bybit.com`；端點只允許 `GET /v5/market/instruments-info`、`/v5/market/kline`、`/v5/market/funding/history`、
   `/v5/market/open-interest`。每個請求的端點與參數組合必須出現在計畫檔的白名單內，否則拒絕。不送任何認證標頭，不讀任何金鑰。
2. 參數與分頁以 [Bybit API 參考](../references/2026-04-04--bybit_api_reference.md) 為準，寫程式前逐條核對，並一律**顯式**送 `limit`：
   - K 線：`limit=1000`（預設只有 200），回應最新在前；以 `start`／`end` 分頁；只保留已收盤的 K 線。
   - 資金費歷史：`limit=200`；只能以時間窗分頁，只傳 `startTime` 會出錯，須帶 `endTime` 並向前走；資金費為 0 或負值都合法。
   - 持倉量：請求鍵是 `intervalTime`，`limit=200`（預設只有 50），以 `cursor` 與時間窗分頁。
   - instruments-info：參考文件**沒有**建立它的分頁與篩選契約，視為未驗證。顯式送 `limit` 與 `category=linear`，沿 `nextPageCursor` 走完；
     cursor 不前進、超過頁數上限、或仍有非空 cursor 卻停止時，一律失敗，不得靜默截斷。保存每一頁的原始回應，
     先由原始回應確認合約類型、結算幣與狀態的欄位名與取值，再寫成篩選規則；篩選規則記入 manifest。
   - 參考文件沒有寫明的其他參數，同樣視為未驗證：照實試、照實記錄回應，不要猜測。
3. 嚴格解析：`retCode` 非 0 即該請求失敗；欄位必須存在且為有限數值；時間戳為整數毫秒。
4. 重試與限額：網路錯誤、HTTP 429 與 5xx 才重試，至多 5 次並退避。收到 HTTP 403 立即停止整個程序並回報——
   參考文件記載，超過每個 IP 每 5 秒 600 次的上限會得到 403，並被封鎖至少 10 分鐘。其他錯誤不重試。
5. 速率：全域每秒至多 4 個請求，命令列只能調低、不能調高。取數的機器可能與交易主機共用出口 IP，所以速率壓在上限的很小一部分。
6. 輸出：每個資料集每個標的一個 `csv.gz`，依時間遞增、去重；另寫一份 `manifest.json`，逐檔記錄資料集、標的、間隔、首尾時間、筆數、缺漏、
   檔案位元組的 SHA-256、取數時間（UTC）、請求數、解析器版本、工具版本與計畫檔的 SHA-256。寫檔先寫暫存檔再取代。缺漏的定義：
   - K 線：應有而缺的根數與區間。
   - 資金費：以該標的的資金費間隔為準，不得假設固定 8 小時；間隔取自 instruments-info，並以相鄰紀錄的實際間隔核對，不一致時照實記錄。
   - 持倉量：以 `intervalTime` 為準，應有而缺的時點與區間。
7. 請求來源（修訂二 N3 的釐清註記）：另寫一份只追加的請求記錄，每個請求一行：端點、完整參數、分頁鏈（第幾頁、所用的 cursor 或時間窗、由哪一頁推得）、
   HTTP 狀態、`retCode`、原始回應位元組的 SHA-256、收到時間。manifest 記下請求記錄檔的 SHA-256，並逐檔指出它由哪些請求組成。
   由請求記錄能核對取數沒有超出計畫檔的範圍。
8. 標的清單與下架品種：除目前交易中的品種外，依計畫檔所列的一次探測，試以狀態查詢已下架的品種，照實記錄回應。
   能取得的下架品種一併按計畫取數；manifest 記下每個標的的上市時間、狀態，以及「期間內是否有下架品種、取得了幾個」。
   這是修訂二 N3 釐清註記所要求的時點清單依據：取不到下架品種時，橫截面假說不得記為候選成立。
9. 可續傳：已存在且雜湊與 manifest 相符、涵蓋所需區間的檔案略過；中斷之後重跑只補缺的部分。
10. 命令列：`--plan <計畫檔>`、`--out <輸出目錄>`、`--max-rps`（不得大於 4）、`--universe-only`（只取 instruments-info 並存下原始回應）、
    `--dry-run`（不連網，依先前存下的 instruments-info 回應與計畫估算請求數與時間；沒有存下的回應即拒絕執行並說明）。
11. `stage2_plan.json` 依 §4 寫成，明列每個資料集的端點與參數，以及下架品種的那一次探測；內容與 §4 一致，不得擴大。

**測試**（`test_r8_public_data.py`，全部離線）：instruments-info 的分頁走完、cursor 不前進與超過頁數上限時失敗；各端點顯式送 `limit`；
其他端點的分頁；K 線最新在前與未收盤 K 線的排除；嚴格解析的各種拒絕（缺欄位、非有限值、`retCode` 非 0）；資金費 0 與負值被接受；
端點與參數白名單；速率上限（以假時鐘驗證）；重試上限、403 立即停止、不重試的錯誤；manifest 雜湊正確；請求記錄與 manifest 的對應（含分頁鏈）；
三種缺漏偵測（含資金費間隔不是 8 小時的標的）；續傳略過；寫檔中斷不留下半個檔案；`--max-rps` 超過 4 被拒；
`--universe-only` 只發 instruments-info 的請求；`--dry-run` 不發請求、沒有存下的回應即拒絕；本模組只匯入標準函式庫（AST 檢查）。

**要求**：

   - 曾判 NO-GO 的假說重新登記：引用原裁決，並寫明與原測試的差異（N1）。
   缺必填欄位即拒絕。以標準化 JSON 的 SHA-256 識別。
2. 預登記簿、試驗帳與 holdout 使用帳都是只追加的 JSONL，每筆含前一筆的雜湊。驗證函式接受一個先前提交的鏈頭雜湊：它必須出現在鏈中，
