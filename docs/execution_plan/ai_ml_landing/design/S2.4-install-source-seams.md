# S2.4 · WP4 Production Install Seam — Corrected Minimum-Coherent Design

- Program: `AIML-LONG-LIVED-LANDING-V2`
- Sprint / session / work package: Sprint 2 / `S2.4` / WP4
- Document state: `DESIGN_READY`; this document is not `SOURCE_READY`, `EFFECT_DONE`, or runtime evidence
- Design correction date: 2026-07-25
- Owned production effect: install the Sprint-2 ALR event-consumer runtime and its exact identity, then leave
  the service installed but inactive
- Explicitly excluded: service start, running attestation, quiesce drill, controller/worker installation,
  broker/order/Decision-Lease effects, Cost-Gate changes, and any claim of profitability

> BOUNDARY BANNER — S2.4 must produce a production-capable but authority-locked install seam. Source and
> disposable tests may prove validation, idempotency, apply/rollback logic, and secret non-serialization.
> They do not prove a target-host install. A production effect is reachable only through a governed Linux
> effect driver after exact-head, dependency, authorization, time-budget, and pre-state checks. S2.4 installs
> the unit **inactive**. S2.5 starts and attests it. S2.1 then performs the controlled quiesce/restore drill.
> No development agent receives trading authority.

## 1. Current truth and admission state

The first WP4 draft is rejected. It contained four load-bearing contradictions:

1. it required `S2.1@EFFECT_DONE` before S2.4 even though a real S2.1 quiesce drill needs the runtime that
   S2.4 installs and S2.5 starts;
2. its production branch returned `EXTERNAL_VERIFICATION_PENDING` unconditionally, so no authorized effect
   could ever be performed;
3. it introduced install adapter/classifier identities that the existing component-effect matrix would reject;
4. it described a user service using `/usr/bin/python3`, a mutable checkout and `PYTHONPATH`, while S2.3
   requires a dedicated non-root identity and content-addressed fixed runtime.

As observed while correcting this design, WP3 / S2.1 is PR `#129`, not a landed predecessor. Its exact state
must be rechecked at implementation intake. The WP3 design and implementation currently describe
`systemctl --user`, while the S2.3 identity contract requires `host_systemd_owns_lifecycle=true` and dedicated
component UIDs. WP3 must be amended to observe and fence the system-level unit defined here before WP4 source
implementation may claim `SOURCE_READY`.

This document may land independently because it changes no source or runtime state. It does not satisfy that
predecessor.

### 1.1 Source dependencies

S2.4 source implementation starts only when all of the following are true:

| Dependency | Required state | Reason |
|---|---|---|
| S2.0 observer bootstrap | `SOURCE_READY` | read-only DB observation seam |
| S2.1 quiesce seam | landed `SOURCE_READY`, rebased onto this unit/identity contract | later drill must target the same system unit |
| S2.2A compatibility | `SOURCE_READY` | exact source/runtime compatibility digest |
| S2.3 sealed build + identity | `SOURCE_READY` | immutable runtime and expected identities |
| Program DAG | corrected source/effect ordering recorded in the canonical delivery projection | prevent the old cycle from being dispatched |

`S2.1@EFFECT_DONE` is **not** an S2.4 effect predecessor.

### 1.2 Correct effect DAG

The only coherent production order is:

```text
S2.0 observer EFFECT_DONE
  -> S2.4 install EFFECT_DONE_INACTIVE
  -> S2.5A bounded initial start + initial running attestation
  -> S2.1 controlled quiesce / static-guard / restore drill
  -> S2.5B final post-drill running attestation
  -> S2.2B ingestion compatibility / LR1 completion
```

The canonical TODO/delivery protocol may still show the older effect order. Updating those projections is a
separate program-governance change and is intentionally outside this document-only correction. Until that
amendment lands, S2.4 production effect admission fails closed with `PROGRAM_DAG_AMENDMENT_REQUIRED`.

## 2. Exact S2.4 scope

S2.4 installs one vertical slice that can genuinely run in Sprint 2:

| Subject | S2.4 responsibility | S2.4 terminal observation |
|---|---|---|
| Host identity | provision `aiml-engine-scanner` user/group and private runtime/state directories | exact UID/GID, ownership and modes observed |
| PG identity and ACL | provision `aiml_engine_scanner` with the S1.3 `scanner_capture_writer` grants and exact local-only auth mapping | role attributes, grants and HBA/auth mapping observed |
| Credential slot | install the engine-scanner credential through protected systemd credential custody | encrypted slot/fingerprint and mode observed; no secret serialized |
| Fixed runtime | install the S2.3 `content_addressed_fixed_path` bundle | content digest and interpreter/module closure observed |
| System unit | install the exact system-level ALR event-consumer unit, daemon-reload, but do not enable or start it | loaded, disabled and inactive; exact fragment digest; no drop-ins |

S2.4 does **not** provision or install the future `controller`, `fit_evaluation`, `serving`, or `deleter`
processes. S2.3 correctly declares their expected identities, but those identities become active only when
their owning sessions have real entrypoints and least-privilege grants to exercise:

- controller/worker source remains owned by `S3.1A`;
- fit/evaluation activation remains owned by its later fitting session;
- serving activation remains owned by the serving integration session;
- deleter activation remains owned by retention apply.

Pre-creating all five roles or secret slots would increase attack surface without a running consumer and would
make rollback ownership ambiguous. Each future component receives its own immutable install-effect receipt.

### 2.1 Observer identity is reused, never recreated

`aiml_observer_ro` is the existing S2.0/S1.1 observation identity. S2.4 must not create, rotate, rename or drop
it. The S2.0 effect intent must include read-only access to `learning.alr_consumer_events` so S2.1 can observe
consumer-session state.

If that grant is absent, S2.0 owns an additive, separately authorized grant. Its rollback may revoke only the
grant that operation added; it may not drop the observer role or revoke pre-existing privileges. S2.4 reports
`OBSERVER_PREREQUISITE_MISSING` and performs no install.

## 3. Immutable receipt model

S2.3 receipts are source facts. S2.4 never edits or “flips” their false fields.

The production effect emits a new immutable `s2_4_install_effect_receipt_v1` that references:

- exact source head and target-host identity;
- `source_compatibility_receipt_v2` digest;
- `sealed_build_receipt_v1` digest and `runtime_content_digest`;
- `expected_identity_receipt_v1` digest;
- S1.3 identity/ACL contract digest;
- S2.0 observer effect receipt digest;
- install plan, authorization, journal and independent postcheck digests;
- per-subject observed installed state;
- `service_enabled=false`, `service_active=false`, and `service_started_by_s2_4=false`;
- all nine development/trading authority grants false.

The receipt may say `APPLIED_INACTIVE` only when every required subject is observed and the unit is loaded,
disabled and inactive. It does not alter these S2.3 facts:

```text
expected_identity_receipt_v1.production_provisioned.* == false
expected_identity_receipt_v1.running_attested.* == false
sealed_build_receipt_v1.boundary.production_installed == false
sealed_build_receipt_v1.boundary.production_running_attested == false
```

Those fields describe what S2.3 itself proved. The S2.4 receipt adds later evidence; it does not rewrite
history.

## 4. Classifier, Registry, routing and closure

The frozen S0.3 program-classifier digest remains byte-identical. This does not mean S2.4 may create adapters
outside classification.

S2.4 source implementation must version the non-frozen sibling component-effect mapping and bind every plan
step to an exact effect class:

| Install-plan step | Component-effect class |
|---|---|
| host UID/group, private directories, PG role/ACL and local auth mapping | `PG_ROLE_ACL_MIGRATION` with an S2.4 production binding |
| first credential-slot installation | a precise `CREDENTIAL_INSTALL` row in the versioned sibling matrix |
| sealed fixed-runtime materialization | `LEARNING_RUNTIME` |
| ALR event-consumer unit installation | `ENGINE_SCANNER` |

`CREDENTIAL_ROTATION` may be reused only for an existing A→B→A rotation. It must not mislabel first
provisioning. `CONTROLLER_WORKERS` is not part of this session. A broad, unclassified
`aiml_component_install` class is forbidden.

The implementation adds:

1. a closed-schema top-level route class, `s2_4_install_plan`;
2. a Registry adapter identity, `s2_4_install_adapter_v1`, whose status is
   `AUTHORITY_LOCKED_PRODUCTION_CAPABLE`, not “apply permanently disabled”;
3. exact route and closure bindings for the plan, result, journal, rollback and postcheck schemas;
4. a component-effect matrix version that maps only the four rows above to reviewed adapter IDs;
5. forward-only surface checks requiring `runtime_effect`, `service`, `pg`, `secret`, high/critical risk and
   `runtime_claim=true`.

No effect node is injected for an ordinary source or documentation task. An admitted effect task receives the
single purpose-built install node only after the exact authorization and dependency receipt set validates.

## 5. Aggregate install transaction

Five independent “successful” adapters are not enough. S2.4 is one recoverable install transaction.

### 5.1 `s2_4_install_plan_v1`

The plan is canonical and self-digested. It contains:

- `plan_id`, `idempotency_key`, exact source head and target-host identity;
- dependency receipt digests and expected pre-state digest;
- four ordered typed steps;
- exact postconditions and compensation for each step;
- aggregate observation window and apply/rollback budgets;
- operator authorization digest and expiry;
- no raw shell, SQL, credential value or arbitrary path.

Required order:

```text
1. host UID/group + private directories
2. PG role/ACL + local auth mapping + protected credential slot
3. content-addressed fixed runtime
4. system unit install + daemon-reload, remaining disabled/inactive
```

The production driver exposes typed methods for those operations. It does not accept caller-provided shell
commands, SQL strings, unit text, users, roles or filesystem roots outside the validated plan.

### 5.2 Durable journal and crash recovery

`s2_4_install_journal_v1` is persisted atomically and fsynced before and after every mutation. Each step records:

- `NOT_STARTED | APPLYING | APPLIED | VERIFYING | VERIFIED | COMPENSATING | COMPENSATED | FAILED`;
- pre-state digest and task-owned delta;
- apply and postcheck evidence digests;
- compensation intent/result;
- no secret bytes.

On startup, the effect runner reconciles any non-terminal journal before accepting a new plan:

- if observed state equals the planned post-state, resume verification;
- if it equals the pre-state, mark the interrupted step not applied and resume safely;
- if it is a task-owned partial state, compensate in reverse order;
- if ownership or state is ambiguous, emit `RECOVERY_REQUIRED` and perform no new mutation.

No result may claim “nothing stranded” without a terminal journal plus an independent residue postcheck.

### 5.3 Failure and compensation

Failure after any applied step triggers reverse-order compensation:

```text
unit -> runtime -> credential/auth/PG -> host directories/identity
```

Rollback is ownership-aware:

- remove only a unit/runtime path whose pre-state proved absent or restore the exact captured prior bytes;
- revoke only grants and HBA/auth rows added by this plan;
- restore an existing role exactly rather than dropping it;
- remove a new role/user/directory only after proving no unrelated owner or consumer exists;
- never drop `aiml_observer_ro`;
- never serialize or reconstruct an old secret from logs or receipts.

If safe exact compensation is impossible, the adapter leaves the service disabled/inactive, emits
`RECOVERY_REQUIRED`, records the exact residual, and blocks S2.5. It must not convert a safe partial state into
`APPLIED_INACTIVE`.

## 6. Production effect driver and reachable apply path

Source readiness must include a real production-capable driver behind a fail-closed authority gate.

`apply_s2_4_install_plan(plan, authorization, driver)` follows this order:

1. validate schema, canonical digests and idempotency key;
2. verify exact source head, Linux target identity and clean deployment source;
3. verify S2.0 effect receipt and every S2.2A/S2.3/S1.3 dependency digest;
4. verify the canonical program DAG amendment;
5. verify a fresh, domain-separated operator SSHSIG over the exact plan digest, source head, target host,
   pre-state digest, expiry and rollback digest;
6. verify no unresolved journal and capture current pre-state;
7. require observed pre-state to equal the signed pre-state;
8. verify the complete apply/observation/rollback time budget fits inside every governing TTL;
9. call the typed production driver;
10. run the independent postcheck and emit the immutable effect receipt.

Production is therefore reachable when the conditions are met. The following cases remain fail-closed:

| Condition | Required result |
|---|---|
| production driver unavailable on Mac/tests | `EXTERNAL_VERIFICATION_PENDING` |
| WP3 or program DAG not aligned | `PROGRAM_DAG_AMENDMENT_REQUIRED` |
| missing/stale/wrong-domain SSHSIG | `AUTHORIZATION_REJECTED` |
| head, host, receipt or pre-state mismatch | `PRECHECK_FAILED` |
| source/disposable target | `SOURCE_SIMULATION_PASS`, all production flags false |
| apply succeeds but postcheck fails and rollback succeeds | `POSTCHECK_FAILED_ROLLED_BACK` |
| interrupted/ambiguous state | `RECOVERY_REQUIRED` |
| exact apply + independent inactive postcheck | `APPLIED_INACTIVE` |

The source/disposable test driver proves logic only. The Linux production driver is the only implementation
allowed to emit `APPLIED_INACTIVE`.

## 7. Secret custody

“No plaintext ingress anywhere” is not physically meaningful: PostgreSQL authentication must consume a
credential. The enforceable rule is:

- no plaintext secret in Git, plan, intent, result, receipt, journal, argv, environment, command capture,
  process title, log, exception, test artifact or durable unencrypted file;
- secret bytes may enter only through a protected one-shot file descriptor or systemd credential directory,
  and may exist transiently in the authorized process memory required for apply/authentication;
- the production driver receives a non-serializable opaque secret handle, never a string value;
- best-effort memory zeroization occurs immediately after the bounded operation;
- fingerprints are domain-separated and non-reversible.

The system unit uses `LoadCredentialEncrypted=` where host capability permits it, and consumes the DSN or
credential from `%d/<credential-name>`. There is no secret-bearing environment fallback and no persistent
plaintext `alr-shadow.dsn`.

Disposable tests generate an ephemeral secret and prove:

1. the intended role connects through the protected handle;
2. an absent or old credential is denied;
3. rollback restores exact authentication state;
4. recursive scans of every serialized artifact contain neither the secret nor common encoded forms.

## 8. Fixed runtime and system unit contract

The current template is not production-eligible. S2.4 implementation replaces these legacy assumptions:

```text
WorkingDirectory=%h/BybitOpenClaw/srv
Environment=PYTHONPATH=...
ExecStart=/usr/bin/python3 ...
user=alr_shadow
systemctl --user
```

The production contract is a **system-level** service because per-component dedicated UIDs cannot be enforced
by one ordinary user's systemd manager.

Illustrative required shape:

```ini
[Service]
Type=exec
User=aiml-engine-scanner
Group=aiml-engine-scanner
WorkingDirectory=/var/lib/arcane-equilibrium/aiml/engine-scanner
LoadCredentialEncrypted=pg-dsn:/etc/credstore.encrypted/aiml-engine-scanner-pg-dsn
Environment=ALR_SOURCE_HEAD=<exact-40-hex-head>
Environment=ALR_EXPECTED_LEARNING_RUNTIME_DIGEST=<exact-digest>
Environment=ALR_EXPECTED_COMPATIBILITY_RECEIPT=<exact-digest>
ExecStart=/opt/arcane-equilibrium/aiml/runtimes/<runtime-content-digest>/bin/python3 -I \
  -m ml_training.alr_event_consumer --dsn-file %d/pg-dsn \
  --lock-file %t/arcane-equilibrium/aiml-engine-scanner/consumer.lock --max-batch 32
RuntimeDirectory=arcane-equilibrium/aiml-engine-scanner
RuntimeDirectoryMode=0700
StateDirectory=arcane-equilibrium/aiml-engine-scanner
StateDirectoryMode=0700
NoNewPrivileges=true
UMask=0077
RestrictAddressFamilies=AF_UNIX
```

The final rendered unit is generated from validated fields, hashed and installed as immutable task-owned
bytes. It contains no mutable checkout path, `PYTHONPATH`, system Python, home-relative path, `alr_shadow`
identity or arbitrary drop-in. The content-addressed runtime contains both the interpreter/dependencies and
the reviewed module tree.

The consumer must be corrected to validate the exact S2.3 identity:

- PG role `aiml_engine_scanner`, not `alr_shadow`;
- an exact local-only endpoint/auth mapping, preferably the reviewed Unix socket;
- database `trading_ai`;
- no `hostaddr`, service file, remote endpoint or environment credential fallback.

S2.4 runs `daemon-reload` only after installing the unit. Its postcheck requires:

```text
LoadState=loaded
ActiveState=inactive
UnitFileState=disabled
NeedDaemonReload=no
FragmentPath=<exact system unit path>
DropInPaths=""
```

S2.4 must not call `enable`, `start`, `restart`, `try-restart`, `reload-or-restart` or send a process signal.
S2.5 owns initial start and running evidence.

## 9. Time and authorization budget

The adapter rejects a plan unless:

```text
apply_budget
+ postcheck_duration
+ postcheck_sample_interval
+ rollback_budget
+ safety_margin
<= min(
     install_intent_remaining_ttl,
     operator_authorization_remaining_ttl,
     dependency_effect_receipt_remaining_ttl
   )
```

For a multi-step operation, either one aggregate authorization covers the full transaction or every step has a
just-in-time permit that also binds the same plan/journal/idempotency key. A 3,600-second observation plan
cannot execute under a 900-second permit. Expiry during apply triggers compensation; expiry never converts a
partial apply into success.

The SSHSIG identity/namespace is dedicated to S2.4 and cannot replay S1/S2.0/S2.1 permits:

```text
identity:  aiml-s2-install-operator-v1
namespace: arcane-equilibrium-aiml-s2-install
payload:   domain || plan_digest || source_head || target_host ||
           pre_state_digest || rollback_digest || issued_at || expires_at
```

An independent verifier re-derives the payload and verifies signer, namespace, freshness and exact receipt
bindings. A self-digest is integrity evidence, not producer authenticity.

## 10. Source implementation inventory

The S2.4 source work package should own only the following bounded surfaces:

| Surface | Required work |
|---|---|
| SSOT adapter | typed plan/apply/reconcile/rollback/postcheck logic and production driver protocol |
| Schemas | plan, step result, journal, rollback, independent postcheck and effect receipt |
| Component matrix | versioned sibling mapping for the four exact install steps |
| Routing/Registry/closure | exact `s2_4_install_plan` wiring and authority-locked adapter registration |
| Runtime consumer | replace `alr_shadow`/mutable-source assumptions with exact S2.3 engine-scanner binding |
| Unit template | system-level, dedicated UID, content-addressed interpreter/module root, protected credential |
| Tests | structure, disposable apply/rollback, crash recovery, classifier, authorization and secret negatives |

It must not add controller/worker entrypoints or pretend future identities are installed.

### 10.1 Required tests

At minimum:

1. schema round-trip and canonical self-digest tests;
2. frozen S0.3 classifier digest unchanged;
3. every step accepted by the versioned component matrix; any adapter substitution rejected;
4. production target without driver/authorization/dependencies returns a typed non-success and performs zero
   mutations;
5. valid disposable apply → independent postcheck → reverse rollback → exact restoration;
6. fail-after-each-step compensation tests;
7. crash at every journal transition, then deterministic reconcile/resume/rollback;
8. idempotent replay with the same key and rejection of same key/different plan;
9. pre-state/head/host/receipt/SSHSIG namespace/freshness mismatch negatives;
10. TTL budget inequality and expiry-during-apply compensation;
11. user service, `/usr/bin/python3`, `PYTHONPATH`, mutable checkout, `alr_shadow`, remote PG and plaintext-secret
    negatives;
12. observer role cannot be created/dropped/revoked by S2.4;
13. source/disposable results cannot set production or running claims;
14. `APPLIED_INACTIVE` requires a distinct Linux postcheck and exact terminal journal;
15. recursive secret/encoded-secret scan of all artifacts;
16. no controller/worker/serving/deleter production activation in WP4.

Real PG integration tests use a throwaway cluster and prove the intended role succeeds, over-grants fail and
rollback restores exact ACL/auth state. They never contact production PG.
