# S2.4 · WP4 Production Install Seam — Corrected Minimum-Coherent Design

- Program: `AIML-LONG-LIVED-LANDING-V2`
- Sprint / session / work package: Sprint 2 / `S2.4` / WP4
- Document state: `DESIGN_READY_EXECUTION_CONTRACT`; source implementation admission remains
  `BLOCKED_W0_ALIGNMENT`
- Design correction date: 2026-07-25
- Owned production effect: install the Sprint-2 ALR event-consumer runtime and its exact identity, then leave
  the service installed but inactive
- Explicitly excluded: installed long-lived service start/running attestation, quiesce drill,
  controller/worker installation, broker/order/Decision-Lease effects, Cost-Gate changes, and any claim of
  profitability

> BOUNDARY BANNER — S2.4 must produce a production-capable but authority-locked install seam. Source and
> disposable tests may prove validation, idempotency, apply/rollback logic, and secret non-serialization.
> They do not prove a target-host install. A production effect is reachable only through a governed Linux
> effect driver after exact-head, dependency, authorization, time-budget, and pre-state checks. S2.4 installs
> the unit **inactive**. S2.5A enables, starts and attests it. S2.1 then performs the controlled
> quiesce/restore drill.
> Signed capability-probe/PREPARE routes may run and fully remove their own bounded transient units; “inactive”
> and “no start” refer to the installed long-lived `arcane-equilibrium-aiml-engine-scanner.service`.
> No development agent receives trading authority.

## 2. Exact S2.4 scope

S2.4 installs one vertical slice that can genuinely run in Sprint 2:

| Subject | S2.4 responsibility | S2.4 terminal observation |
|---|---|---|
| Host identity | provision `aiml-engine-scanner` user/group plus static state/config/install parents; render runtime-directory directives only | exact UID/GID, static ownership/modes and unit directives observed; no runtime-directory existence claim |
| PG identity and ACL | provision `aiml_engine_scanner` with the S1.3 `scanner_capture_writer` grants on the attested cluster behind runtime endpoint `127.0.0.1:5432/trading_ai`, SCRAM only | runtime/admin endpoint mapping, cluster identity, role attributes, grants and effective HBA/auth mapping observed |
| Credential slot | install the engine-scanner credential through mandatory encrypted systemd credential custody | encrypted slot/fingerprint and mode observed; no secret serialized |
| Sealed base runtime | materialize the S2.3 `content_addressed_fixed_path` dependency runtime | S2.3 `runtime_content_digest` and interpreter/native closure observed |
| Application + launch bundle | install the reviewed application files separately, then derive a launch tree binding app and base runtime | `application_bundle_digest` and `launch_bundle_digest` independently observed |
| Candidate-learning configuration | render the non-secret candidate policy from the reviewed template and create the private evidence rendezvous | exact `policy_config_hash`, root-owned policy bytes and empty/task-owned evidence directory observed |
| System unit | install the exact system-level ALR event-consumer unit, daemon-reload, but do not enable or start it | loaded, disabled and inactive; exact fragment digest; no drop-ins |

S2.4 does **not** provision or install the future `controller`, `fit_evaluation`, `serving`, or `deleter`
processes. S2.3 correctly declares their expected identities, but those identities become active only when
their owning sessions have real entrypoints and least-privilege grants to exercise:

- controller/worker source remains owned by `S3.1A`;
- fit/evaluation activation remains owned by its later fitting session;
- serving activation remains owned by the serving integration session;
- deleter activation remains owned by retention apply.

Pre-creating all five roles or secret slots would increase attack surface without a running consumer and would
make rollback ownership ambiguous. Each future component receives its own immutable install-effect receipt.

### 2.1 Engine-scanner SQL boundary and retention split

The current `alr_event_consumer.py` unconditionally calls the retention repository, whose decisions can
`UPDATE` and `DELETE` derived-cache rows. That behavior is incompatible with an
`aiml_engine_scanner`/`scanner_capture_writer` identity and with the separately owned future `deleter`.

WP4 must remove the retention pass from every engine-scanner execution path before packaging:

- the engine-scanner process must neither import nor call the retention apply repository;
- its traced SQL surface contains no retention-table mutation and no `DELETE`;
- retention source may remain in the repository, but is unreachable from this unit;
- a later session creates a distinct deleter entrypoint, UID, PG role, authorization and receipt.

Expanding the engine-scanner ACL to make the existing mixed-responsibility entrypoint run is forbidden. Until
the split and a closed `pg_acl_manifest_v1` both pass, return `ENGINE_SCANNER_PRIVILEGE_SPLIT_REQUIRED`.

`pg_acl_manifest_v1` is a canonical, hash-bound allowlist of every database, schema, table, sequence and
function privilege required by the post-split entrypoint. It grants no wildcard/default privilege, ownership,
role membership, `GRANT OPTION`, schema create, database create/temp, replication or `BYPASSRLS`. A static SQL
inventory plus disposable-PG trace must match it exactly; an unlisted statement or over-grant fails W2/W3.

### 2.2 Observer identity is reused, never recreated

`aiml_observer_ro` is the existing S2.0/S1.1 observation identity. S2.4 must not create, rotate, rename or drop
it. The S2.0 effect intent must include read-only access to `learning.alr_consumer_events` so S2.1 can observe
consumer-session state.

If that grant is absent, S2.0 owns an additive, separately authorized grant. Its rollback may revoke only the
grant that operation added; it may not drop the observer role or revoke pre-existing privileges. S2.4 reports
`OBSERVER_PREREQUISITE_MISSING` and performs no install.

## 3. Immutable receipt model

S2.3 receipts are source facts. S2.4 never edits or “flips” their false fields.

The production effect emits a new immutable `s2_4_install_effect_receipt_v1` that references:

- exact source head and target-host identity;
- `source_compatibility_receipt_v2` digest;
- `sealed_build_receipt_v1` digest and `runtime_content_digest`;
- `s2_4_source_admission_receipt_v1`, W0-W5 wave-chain and dependency-refresh digests;
- terminal `s2_4_prepare_effect_receipt_v1`, `s2_4_prepared_install_bundle_v1`,
  `base_runtime_tree_manifest_v1` and
  `base_runtime_tree_digest`;
- `application_bundle_manifest_v1` digest and `application_bundle_digest`;
- `launch_bundle_manifest_v1` digest, `launch_bundle_digest` and rendered launcher-config digest;
- `expected_identity_receipt_v1` digest;
- S1.3 identity contract plus exact `pg_acl_manifest_v1` digest;
- S2.0 observer effect receipt digest;
- exact `pg_topology_attestation_v1` digest, independent PG-migration permit digest and encrypted
  credential-slot blob fingerprint;
- exact signed HBA pre-state/delta/expected-post/rollback projection and post-mutation topology digest;
- terminal capability-probe effect receipts and exact
  `network_sandbox_capability_attestation_v1(scope=PREPARE_SANDBOX|INSTALLED_UNIT)` digests/expiries;
- native-loader closure/postcheck digest;
- candidate-policy config hash and candidate-evidence directory ownership digest;
- install plan, prepare/aggregate/PG authorization, replay-ledger, journal and independent postcheck digests;
- per-subject observed installed state;
- `service_enabled=false`, `service_active=false`, and `service_started_by_s2_4=false`;
- all nine development/trading authority grants false.

The receipt may say `APPLIED_INACTIVE` only when every required subject is observed and the unit is loaded,
disabled and inactive. It does not alter these S2.3 facts:

```text
expected_identity_receipt_v1.production_provisioned.* == false
expected_identity_receipt_v1.running_attested.* == false
sealed_build_receipt_v1.boundary.production_installed == false
sealed_build_receipt_v1.boundary.production_running_attested == false
```

Those fields describe what S2.3 itself proved. The S2.4 receipt adds later evidence; it does not rewrite
history.

probe/prepare/plan/idempotency/pre-state lineage.

1. closed-schema top-level route classes `s2_4_capability_probe_intent`, `s2_4_prepare_intent` and
   `s2_4_install_plan`;
2. Registry adapter identities `s2_4_capability_probe_adapter_v1`, `s2_4_prepare_adapter_v1` and
   `s2_4_install_adapter_v1`, all

3. exact route and closure bindings for PREPARE/APPLY core, intent/plan, result, journal, rollback and
   postcheck schemas;
4. the additive v2 component-effect matrix described above, mapping only the seven classes above to reviewed

5. forward-only, per-route surface checks from this closed matrix:

| Route | Required effect class/surfaces | Explicitly forbidden surfaces |
|---|---|---|
| `s2_4_capability_probe_intent` | only `HOST_CAPABILITY_PROBE`; `runtime_effect=true`, `service=transient_probe_only`, high risk, `runtime_claim=true`, exact probe/cleanup budget | persistent unit write/enable/start, daemon-reload, PG/migration/secret/credential/host identity, broker/order |
| `s2_4_prepare_intent` | only `LEARNING_RUNTIME_PREPARE`; `runtime_effect=true`, `service=transient_builder_only`, high risk, `runtime_claim=true`, exact staging/fetch/build/cleanup budgets | persistent unit write/enable/start, daemon-reload, PG/migration/secret, credential install, host identity, `/opt`, `/etc`, broker/order |

Registry, route, closure and central-validator outputs independently derive this matrix. A PREPARE request
carrying any APPLY surface or a probe request carrying builder/install authority is rejected before node
injection; no union of routes or caller-provided surface list is accepted. Transient units use unpredictable
task-bound names, `RuntimeMaxSec`, fixed sandbox properties and a journaled stop/reset-failed/remove postcheck;
they cannot write `/etc/systemd/system`, call daemon-reload or survive their authorized operation.

No effect node is injected for an ordinary source or documentation task. W6A first receives one
`PREPARE_SANDBOX` capability-probe node and, after its terminal receipt, one purpose-built PREPARE node. W6B
first receives one `INSTALLED_UNIT` capability-probe node and, after its terminal receipt and final
authorizations, only the APPLY coordinator.

## 5. Aggregate install transaction

Six independent “successful” effects are not enough. S2.4 is one prepare lineage plus one recoverable install
transaction.

### 5.1 `PREPARE -> sign -> APPLY`

The production tree cannot be named safely before it exists. S2.4 therefore has two separately authorized
install phases plus one narrowly authorized capability probe immediately before each phase. Building and
signing a plan in the opposite order is forbidden:

```text
sign PREPARE_SANDBOX probe core -> run/close probe -> terminal probe receipt
  -> build/sign PREPARE core containing that receipt -> run/close PREPARE -> terminal prepare receipt
  -> render exact final unit
  -> sign INSTALLED_UNIT probe core -> run/close probe -> terminal probe receipt
  -> build final plan core containing both probe receipts + prepare receipt
  -> sign aggregate + PG permits -> APPLY
```

There is no digest/signature cycle. Every governed envelope uses an unsigned canonical core:

```text
probe_core_digest   = digest(s2_4_capability_probe_core_v1)
probe_id            = "s2-4-probe-" + hex(probe_core_digest)
probe_auth          = SSHSIG(probe_core_digest, probe_id, scope, ...)

prepare_core_digest = digest(s2_4_prepare_core_v1)
prepare_id          = "s2-4-prepare-" + hex(prepare_core_digest)
prepare_auth        = SSHSIG(prepare_core_digest, prepare_id, ...)

plan_core_digest    = digest(s2_4_install_plan_core_v1)
plan_id             = "s2-4-" + hex(plan_core_digest)
idempotency_key     = plan_id
aggregate_auth      = SSHSIG(plan_core_digest, plan_id, ...)
pg_auth             = SSHSIG(plan_core_digest, plan_id, topology_digest,
                             installed_unit_probe_receipt_digest, acl_digest,
                             hba_delta_digest, ...)
```

Core schemas exclude IDs, authorization objects/signatures and final self-digests. Authorizations are separate
artifacts in `authorization_set`; they are not embedded into or hashed by any core/plan. Final probe
intent/PREPARE intent/install plan artifacts contain `{core, core_digest, derived_id, self_digest}` and
validators independently re-derive every field. `authorization_id` is likewise derived from its unsigned
payload before the SSHSIG is attached. The plan core declares only required authorization profile IDs/domains
and maximum-TTL policy; actual
authorization IDs, digests, expiries and signatures exist solely in `authorization_set`.

1. `s2_4_prepare_intent_v1` binds the prepare core/source head, S2.3 lock/closure identity, target platform,
   application manifest, maximum bytes/time, a private staging root and a pre-W6A
   terminal `s2_4_capability_probe_effect_receipt_v1(scope=PREPARE_SANDBOX)` over the fixed fetch/build
   sandbox properties. A separate prepare-only SSHSIG binds its core digest. The prepare driver may
   fetch hash-pinned wheels and materialize files only below
   `/var/lib/arcane-equilibrium/aiml/install/s2_4/prepared/<prepare_id>/`; it cannot publish into `/opt`, change
   UID/PG/credential/persistent-unit state, or start the installed `arcane-equilibrium-aiml-engine-scanner.service`. It may
   start/stop only its exact task-bound transient fetch/build units under the PREPARE route.
2. The prepare driver emits `s2_4_prepared_install_bundle_v1`, including immutable artifact locators,
   `base_runtime_tree_manifest_v1`/digest, application digest, launch-tree manifest/digest, native import proof,
   staging device/inode and an expiry. Staging remains root-owned/non-writable and is independently re-hashed.
   After the bundle digest is fixed, PREPARE closes/fsyncs its journal, runs the independent residue postcheck
   and emits `s2_4_prepare_effect_receipt_v1` binding intent/authorization, bundle, terminal journal, consumed
   replay entry, postcheck and rollback digests. The bundle does not hash that receipt or journal.
3. Only then does the operator sign `s2_4_install_plan_v1`, binding the exact prepare effect receipt/bundle and
   every final digest/path/pre-state/rollback. APPLY re-hashes staging, atomically publishes same-filesystem
   trees into the fixed `/opt` roots, and performs the remaining typed steps.

Expired, missing, cross-device, changed or already-consumed prepare artifacts return
`PREPARED_BUNDLE_INVALID`. The prepare adapter's signed rollback digest grants compensation of only that
prepare journal's task-owned staging delta even after apply authority expires; expiry blocks new/resumed apply
but not safety rollback. There is no age-scan or separate cleanup shortcut.

The install plan is canonical and self-digested. It contains:

- `plan_id`, `idempotency_key`, exact source head and target-host identity;
- dependency/refresh/topology, both terminal capability-probe and PREPARE receipt digests, signed HBA
  projection digest and expected pre-state digest;
- six ordered typed steps;
- exact postconditions and compensation for each step;
- aggregate observation window and apply/rollback budgets;
- required PREPARE-lineage, aggregate and PG authorization profile/domain/maximum-TTL policies, but no actual
  authorization object, digest, expiry or signature;
- no raw shell, SQL, credential value or arbitrary path.

Required order:

```text
1. host UID/group + private directories
2. PG role/ACL + exact local auth mapping
3. encrypted credential-slot installation
4. publish the prepared content-addressed sealed base runtime
5. application bundle + derived launch bundle
6. validated candidate policy + private evidence directory + system unit install + daemon-reload, remaining
   disabled/inactive
```

The production driver exposes typed methods for those operations. It does not accept caller-provided shell
commands, SQL strings, unit text, users, roles or filesystem roots outside the validated plan.

The PG step carries a closed `s2_4_pg_hba_delta_v1`, signed by both the aggregate and PG permits. It binds the
attested pre-HBA bytes/digest, either one normalized task-owned row addition or an exact no-op, its insertion
anchor, expected full post-HBA bytes/digest/effective rule, reload operation, and exact rollback projection.
Postcheck requires every non-HBA topology field to remain identical and HBA state to equal only that expected
post projection. Rollback requires the projected pre-state. A listener/proxy/cluster change or any HBA change
outside the signed delta is `PG_TOPOLOGY_UNPROVEN`; the authorized projected row itself is not topology drift.

### 5.2 Durable journal and crash recovery

Exactly one writer may own an install transaction. The runner acquires
`/run/lock/arcane-equilibrium-aiml-s2-4-install.lock` with non-blocking exclusive `flock`; contention returns
`INSTALL_LOCK_HELD` with zero mutation.

The runner opens the verified root-owned `/run/lock` parent by directory FD using
`O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`, binds its device/inode/mode, and opens the fixed lock basename with
`openat(O_NOFOLLOW|O_CREAT|O_CLOEXEC, 0600)`. `fstat` must prove a root-owned regular file, mode `0600`, link
count one and the expected device before `flock`. The lock is never unlinked; a symlink, hardlink, replaced
parent or permissive ownership/mode returns `PRECHECK_FAILED`.

Each capability probe, PREPARE and APPLY has its own WAL:

```text
/var/lib/arcane-equilibrium/aiml/install/s2_4/probes/<probe_id>.probe.journal.json
/var/lib/arcane-equilibrium/aiml/install/s2_4/prepared/<prepare_id>.prepare.journal.json
/var/lib/arcane-equilibrium/aiml/install/s2_4/<plan_id>.journal.json
```

Before the first transient-unit D-Bus call, `s2_4_capability_probe_journal_v1` records/fsyncs `APPLYING` with
the exact derived unit name
`arcane-aiml-s2-4-probe-<64-lowercase-hex>.service`, scope, complete property digest, expected
InvocationID/cgroup pattern and cleanup rollback digest. It then journals unit creation, observation,
stop/kill-after-grace, reset-failed/removal and zero-residue verification as separate transitions. A restarted
runner holding the install lock first inspects that exact unit name, InvocationID and cgroup:

- exact task-owned live/failed state is stopped, its cgroup is boundedly drained, reset/removed and independently
  verified absent;
- already absent state with complete observation evidence resumes only cleanup/postcheck finalization;
- a mismatched unit/property/InvocationID, ambiguous cgroup or malformed journal returns `RECOVERY_REQUIRED`
  without starting another unit.

The signed probe rollback digest remains authority only for this exact stop/drain/reset/remove compensation
after probe authorization expiry. Expiry forbids new creation or observation resumption; it cannot block
safety cleanup. A terminal probe receipt requires a terminal journal and absence from systemd unit lists,
cgroup/process state and task-owned transient files.

`s2_4_prepare_journal_v1` records `PREPARING` and fsyncs **before** creating the staging directory, so a crash
before the prepared receipt still has task ownership/reconcile evidence. Its reconcile path either resumes
from independently observed files or compensates only that staging delta. `s2_4_install_journal_v1` owns the
later APPLY transaction.

Parents are root-owned mode `0700`; journals are root-owned mode `0600`. Every update uses same-filesystem
temporary creation, file `fsync`, atomic rename and parent-directory `fsync`. Each journal has a canonical
self-digest plus an outer checksum. Malformed, truncated or checksum-invalid bytes return
`JOURNAL_CORRUPT_RECOVERY_REQUIRED`; they are never renamed away or overwritten automatically.

`probe_id` is exactly `s2-4-probe-` plus 64 lowercase hex characters from `probe_core_digest`; `prepare_id` is
exactly `s2-4-prepare-` plus 64 lowercase hex characters from `prepare_core_digest`; `plan_id` is exactly
`s2-4-` plus 64 lowercase hex characters from `plan_core_digest`. For all three paths, the driver opens a
previously verified parent directory FD (`O_DIRECTORY|O_NOFOLLOW`), binds its device/inode and link count, and
uses `openat` with `O_NOFOLLOW|O_CREAT|O_EXCL`; it never joins an unchecked caller string into a root path.
Parent replacement, symlink, hardlink or cross-device staging returns `PRECHECK_FAILED`.

Each step records:

- `NOT_STARTED | APPLYING | APPLIED | VERIFYING | VERIFIED | COMPENSATING | COMPENSATED | FAILED`;
- pre-state digest and task-owned delta;
- apply and postcheck evidence digests;
- compensation intent/result;
- no secret bytes.

The journal is a write-ahead log, not a retrospective log:

1. write and fsync `APPLYING` with the exact operation ID and expected pre/post-state **before** the external
   effect;
2. execute one typed effect;
3. independently re-observe the subject;
4. write and fsync `APPLIED` with the observed digest, then enter `VERIFYING`.

A crash in `APPLYING` is reconciled from observed state and is never blindly replayed. Fault injection covers
the windows immediately before the effect, after the effect but before observation, and after observation but
before `APPLIED` fsync.

On startup, the effect runner reconciles any non-terminal probe/PREPARE/APPLY journal before accepting a new
probe, prepare intent or plan:

- if observed state equals the planned post-state, resume verification;
- if it equals the pre-state, mark the interrupted step not applied and resume safely;
- if it is a task-owned partial state, compensate in reverse order;
- if ownership or state is ambiguous, emit `RECOVERY_REQUIRED` and perform no new mutation.

No result may claim “nothing stranded” without a terminal journal plus an independent residue postcheck.

### 5.3 Pre-existing-state decision matrix

Every resource is classified before the first mutation:

| Observed state | Required action |
|---|---|
| absent | create and mark the exact delta task-owned |
| exact desired state plus matching prior S2.4 receipt/journal | idempotent `NOOP_VERIFIED` |
| exact desired bytes/state without matching ownership evidence | `PREEXISTING_UNOWNED_STATE`; no adoption |
| different pre-existing bytes/state | `PRESTATE_MISMATCH`; no overwrite |
| partial task-owned state with valid journal | deterministic reconcile, resume or compensate |
| partial state without a valid task-owned journal | `RECOVERY_REQUIRED`; no mutation |
| credential slot already exists without matching task ownership | `PREEXISTING_UNOWNED_STATE`; no read, backup, adoption or rotation |

### 5.4 Failure and compensation

Failure after any applied step triggers reverse-order compensation:

```text
unit -> launch/application bundle -> base runtime -> credential -> auth/PG -> host directories/identity
```

Rollback is ownership-aware:

- remove only a unit/runtime/application path whose pre-state proved absent and whose journal records task
  ownership, or restore exact non-secret captured prior bytes;
- revoke only grants and HBA/auth rows added by this plan, reproducing the signed HBA rollback projection;
- after any unit-byte rollback, run the typed `daemon-reload` operation again and verify the restored exact
  `FragmentPath`/digest/load state;
- after any HBA rollback, use the topology-attested reload operation ID, then verify active HBA rules,
  cluster identity and runtime/admin connectivity state;
- restore an existing role exactly rather than dropping it;
- remove a new role/user/directory only after proving no unrelated owner or consumer exists;
- never drop `aiml_observer_ro`;
- never read, serialize, back up or reconstruct a pre-existing secret from logs, receipts or rollback state.

If safe exact compensation is impossible, the adapter leaves the service disabled/inactive, emits
`RECOVERY_REQUIRED`, records the exact residual, and blocks S2.5. It must not convert a safe partial state into
`APPLIED_INACTIVE`.

## 7. Secret custody

“No plaintext ingress anywhere” is not physically meaningful: PostgreSQL authentication must consume a
credential. The enforceable rule is:

- no plaintext secret in Git, plan, intent, result, receipt, journal, argv, environment, command capture,
  process title, log, exception, test artifact or durable unencrypted file;
- secret bytes may enter only through a protected one-shot file descriptor or systemd credential directory,
  and may exist transiently in the authorized process memory required for apply/authentication;
- the production driver receives a non-serializable opaque secret handle, never a string value;
- best-effort memory zeroization occurs immediately after the bounded operation;
- fingerprints are domain-separated and non-reversible.

The reviewed Linux target supports systemd encrypted credentials. `LoadCredentialEncrypted=` is therefore
mandatory, not a worker-selected option:

```text
encrypted slot: /etc/credstore.encrypted/aiml-engine-scanner-pg-dsn
unit name:      pg-dsn
process path:   %d/pg-dsn
encryption:     systemd-creds encrypt --name=pg-dsn --with-key=host+tpm2
```

The encrypted slot is installed atomically as root-owned mode `0600`; the production driver receives only a
non-serializable credential handle/FD. There is no plaintext file, secret-bearing environment variable,
command-line secret or fallback path. If encrypted credential custody cannot be established, the exact result
is `HOST_CREDENTIAL_CAPABILITY_UNSATISFIED`, with zero PG/unit mutation.

First provisioning uses one fixed in-process `s2_4_secret_broker_v1` inside the authorized aggregate
coordinator; it has no top-level route and accepts no caller-supplied secret. After all permits/pre-state checks
pass, it obtains a high-entropy password from the kernel CSPRNG in locked, non-dumpable memory and creates two
single-consumer sealed FD handles:

1. the PG actor consumes one handle only in the fixed parameterized create/alter-role operation;
2. the credential actor consumes the other to render the closed DSN directly into
   `systemd-creds encrypt --name=pg-dsn --with-key=host+tpm2` over protected FDs;
3. after atomic encrypted-slot install, an independent postcheck decrypts through systemd credential custody
   and proves an end-to-end login as `aiml_engine_scanner` against the attested cluster;
4. every handle is operation-ID-bound, non-seekable/read-once where supported, closed immediately, and its
   backing memory is zeroized. No actor may return or log secret bytes.

The broker prepares the encrypted blob before the first PG mutation but does not publish it until the PG step
has verified. If the later credential install/login check fails, compensation removes a newly task-owned role
or restores a prior task-owned A→B→A rotation from the previous encrypted slot. A pre-existing role or slot
without a matching S2.4 ownership receipt is never re-passworded, adopted or overwritten. Consequently first
provisioning and later rotation have separate pre-state/rollback cases, and no rollback depends on recovering
an unknown plaintext password.

The receipt fingerprint is `sha256` of the encrypted credential blob bytes plus its fixed
name/path/owner/mode metadata. It is never a digest of the password or plaintext DSN. Decryption-name
verification must remain enabled.

The decrypted credential uses a closed libpq key set:

```text
host=127.0.0.1
port=5432
dbname=trading_ai
user=aiml_engine_scanner
password=<non-empty secret>
connect_timeout=5
application_name=arcane-equilibrium-alr-engine-scanner
sslmode=disable
```

Missing keys, additional keys or any `passfile`, `service`, `servicefile`, `sslkey`, `options`, `hostaddr` or
environment-derived value fail before connection. The unit unsets all `PG*` routing/credential variables used
by libpq, and the consumer sets and verifies `PR_SET_DUMPABLE=0` before reading `%d/pg-dsn`. Core dumps are
disabled.

The candidate policy is not a secret, but it is execution identity. Its four non-default budget fields
(`row_budget`, `byte_budget`, `collection_window_days`, `max_new_entries_per_window`) must be non-null,
schema-valid and supplied by the signed install plan. The source worker does not invent production values.
The renderer independently derives `policy_config_hash`; a missing, placeholder or mismatched configuration
returns `CANDIDATE_POLICY_CONFIGURATION_REQUIRED` before any host mutation.

Disposable tests generate an ephemeral secret and prove:

1. the intended role connects through the protected handle;
2. an absent or old credential is denied;
3. rollback restores exact authentication state;
4. recursive scans of every serialized artifact contain neither the secret nor common encoded forms.

### 8.1 Four non-interchangeable content identities

S2.3 `runtime_content_digest` binds the lock closure, interpreter/native inventory and isolated launch
configuration. It does **not** bind `alr_event_consumer.py` or the reviewed application source. S2.4 must not
overload or reinterpret it, and it is not an installed-tree hash.

1. `runtime_content_digest`: unchanged S2.3 lock/config/platform identity.
2. `base_runtime_tree_digest`: canonical digest of `base_runtime_tree_manifest_v1`, created in PREPARE from
   the actual installed staging tree. Sorted entries bind `{path, type, mode, sha256}` plus interpreter target,
   native-library inventory, `runtime_content_digest`, platform and build-tool versions.
3. `application_bundle_digest`: canonical digest of `application_bundle_manifest_v1`, whose sorted entries are
   `{path, mode, sha256}` plus source head, entrypoint, `learning_runtime_digest_v2`, bundle-layout version and
   required runtime resources.
4. `launch_bundle_digest`: canonical digest of `launch_bundle_manifest_v1`, binding
   `{runtime_content_digest, base_runtime_tree_digest, application_bundle_digest, launcher_config_digest,
   launch_tree_digest, target_platform}`. `launch_tree_digest` independently hashes the sorted materialized
   launch-tree `{path, type, mode, sha256}` entries.

The application manifest is produced from a checked-in, reviewable runtime-closure allowlist. It must include
the entrypoint, its local import/resource closure, all v2 learning-runtime manifest inputs, exact compatibility
receipts, schemas, SQL fingerprints, dependency lock/spec and policy template needed by runtime preflight.
Every path is a committed blob at the bound source head. The builder rejects:

- tests, caches, `.pyc`, `.git`, mutable generated output and undeclared files;
- effect-capable deployment/rollback drivers, broker/order modules and credential material;
- symlinks, devices, sockets, world-writable files and any path escaping the bundle root;
- a runtime read/import that escapes the declared manifest.

The prepared base tree is published at
`/opt/arcane-equilibrium/aiml/runtimes/<base_runtime_tree_digest>/`; the S2.3
`runtime_content_digest` remains receipt metadata and is never used as a substitute for that leaf name. A
derived launch tree at
`/opt/arcane-equilibrium/aiml/launches/<launch_bundle_digest>/` materializes the sealed interpreter/dependencies
plus the reviewed application package in its own site-packages. It does not mutate the S2.3 base runtime.
The immutable application source tree is retained at
`/opt/arcane-equilibrium/aiml/apps/<application_bundle_digest>/` for independent re-hash.
All three install parents (`runtimes`, `apps`, `launches`) are `root:root 0755`; every digest leaf and
subdirectory is `root:root 0555`; immutable data files are `0444` and executables/shared libraries are `0555`
as recorded by the manifest. Extended ACLs and mutable checkout links are forbidden. The service can
traverse/read but cannot write. Python is launched with `-B` so bytecode writes are not required.

PREPARE may use the target-platform-attested `/usr/bin/python3.12` only as a bootstrap builder. It records the binary,
package and stdlib digests, copies the interpreter and complete stdlib into staging, installs only
`requirements-ml.lock` wheels fetched with isolated/no-config `--only-binary=:all: --require-hashes`, and records
the wheel bytes. The resulting interpreter must report `sys.executable`, `sys.prefix`, `sys.base_prefix`,
stdlib, site-packages and imported module paths entirely inside the prepared tree; only the explicitly
inventoried target-platform shared libraries may resolve outside. APPLY performs no package/network fetch.
Any system-Python or external-site-packages fallback fails the base-tree postcheck.

PREPARE is split into two sandboxed subphases. `FETCH_BYTES` runs as an unprivileged transient identity with a
closed artifact-mirror allowlist, byte/time limits and no credential/state-directory access; it downloads but
does not import or execute dependency code. `BUILD_AND_IMPORT` runs as a separate transient `DynamicUser` with
no network, no supplementary groups, `NoNewPrivileges`, private tmp/devices/home, strict filesystem protection,
write access only to the exact task-owned staging directory, and explicit CPU/memory/process/time limits.
Root creates/verifies the staging parent and later re-hashes/freezes the result but never executes dependency
Python or native import code. The PREPARE receipt binds both sandbox unit-property digests, artifact hashes,
resource-use results and zero access to `/etc/credstore*`, PG admin handles, application state or broker/order
surfaces.

The base manifest's native-loader closure lists every permitted external shared-library realpath, device/inode,
mode, package identity and digest plus the interpreter's resolved loader search. APPLY independently re-runs
loader resolution and hashes those exact external bytes into its postcheck; S2.5A repeats this before start.
Any new path, changed byte, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONHOME`, `PYTHONPATH` or ambient site-packages
input fails closed. “Only external reads” below means application data reads; the separately attested native
loader closure is the only executable-library exception.

The consumer adds a required `--application-root` argument and recomputes compatibility from that immutable
bundle root using the pinned source-head value. It must not call Git or require a checkout at runtime. An
undeclared file read, module import, manifest drift, digest mismatch or ambient `PYTHONPATH` produces a pre-DB
fail-closed error.

topology-guard and candidate evidence paths, apart from the exact native-loader closure above. Permanent pre-DB
configuration/identity/credential-format failures exit `78`. A transient attested-DB availability failure does
**not** exit: the resident consumer closes the failed connection, preserves its durable cursor semantics and
retries indefinitely with bounded exponential backoff plus jitter (5 seconds minimum, 300 seconds maximum),
without accumulating tasks, rows or memory. The start limit therefore protects actual process crash loops,
while a prolonged database outage cannot exhaust it or permanently stop autonomous collection. Reconnection
must load and self-digest the immutable topology guard, then compare the connected user/database/endpoint and
the exact `learning.alr_runtime_cluster_identity_v1` row to it before consumption resumes. A mismatch exits
`78`; this is an executable in-band cluster-identity check, not a claim that the unprivileged consumer can
inspect host listener/proxy processes.

## 9. Time and authorization budget

The adapter rejects a plan unless:

```text
apply_budget
+ postcheck_duration
+ postcheck_sample_interval
+ rollback_budget
+ safety_margin
<= min(
     install_intent_remaining_ttl,
     operator_authorization_remaining_ttl,
     pg_migration_authorization_remaining_ttl,
     topology_attestation_remaining_ttl,
     installed_unit_probe_receipt_remaining_ttl,
     prepared_bundle_remaining_ttl,
     dependency_effect_receipt_remaining_ttl
   )
```

PREPARE uses a separate inequality over
`fetch_budget + build_import_budget + prepare_postcheck + prepare_rollback + safety_margin`, bounded by only
the PREPARE SSHSIG, terminal `PREPARE_SANDBOX` capability-probe receipt, target-platform and source-dependency
TTLs. Each capability probe has its own `probe + cleanup + independent_postcheck + safety_margin` inequality
bounded by its probe SSHSIG. PREPARE does not depend on a final unit, PG topology, HBA delta or W6B permit.

The aggregate permit covers the full transaction, but it never replaces the mandatory narrower PG migration
permit. Both bind the same plan/journal/idempotency/pre-state and compensation chain. A 3,600-second operation
cannot execute under a 900-second permit. Expiry during apply triggers compensation; expiry never converts a
partial apply into success.

### 9.2 Dependency freshness

Original source receipts are immutable and never have their timestamps rewritten. W5/W6 classify dependencies:

| Evidence | Freshness rule |
|---|---|
| S2.2A compatibility, S2.3 sealed-build/expected-identity and S1.3 contract | exact source/content identities; if their original observation TTL is elapsed, an independently recomputed `s2_4_dependency_refresh_attestation_v1` must bind the original digest, current exact head, reproduced semantic digests and a new short expiry |

The central validator accepts an expired source-identity receipt only together with one current refresh
attestation that independently replays its producer/semantic checks. A refresh cannot refresh another refresh,
cannot change any semantic digest and cannot substitute for runtime observation.
